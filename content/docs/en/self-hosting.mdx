Self-hosting requires two files (`docker-compose.yml` and `.env`) plus `docker compose up -d`. Both files live in the [Customermates repo](https://github.com/customermates/customermates) and you fetch them with `curl`. No `git clone` and no build step are needed. The published image at `ghcr.io/customermates/customermates:latest` applies database migrations on first boot.

## Self-host vs cloud

Self-hosting uses the Starter entitlement baseline. It includes the core CRM records, views, audit logging, REST, webhooks and MCP for an external AI client that you select and fund. It does not include connected messaging accounts, the unified inbox, connected calendar view, hosted Mate or hosted AI credits. Paying for another cloud plan does not expand the self-hosted entitlement set.

| Decision factor                      | Managed cloud                                                                   | Self-hosted                                                              |
| ------------------------------------ | ------------------------------------------------------------------------------- | ------------------------------------------------------------------------ |
| Application and database operations  | Customermates operates them                                                     | You operate Docker, PostgreSQL, network access, TLS, updates and backups |
| Core CRM records and views           | Included by plan                                                                | Starter baseline                                                         |
| Unified inbox and connected calendar | Available on entitled cloud plans                                               | Not included                                                             |
| AI access                            | External MCP; hosted Mate capability remains release-gated                      | External MCP with your own client and provider                           |
| Connected providers                  | Configured within the managed product                                           | You configure and assess every external provider                         |
| Pricing                              | Per-user cloud subscription from [[commercial.price.starter.monthly]] per month | Your infrastructure, providers and operator time                         |

Self-hosting lets you choose where the application and database run. It does not create a security, compliance, privacy or air-gap guarantee by itself. Your organization remains responsible for configuration, providers, contracts, retention and operating controls.

Compare total operating cost rather than assuming one model is cheaper. Include infrastructure, backups, restore testing, monitoring, updates, incident response and external providers as well as any subscription price.

Customermates exports and imports CRM records as Excel workbooks, one entity type at a time, so a working set can move between systems. A whole-platform migration is still a separately designed and validated project.

## Install

### Prerequisites

- Docker and Docker Compose v2.
- A domain name if you want TLS (optional for local).

<Steps>
<Step title="Create a directory and fetch the two config files">
```bash
mkdir customermates && cd customermates
curl -fsSL https://raw.githubusercontent.com/customermates/customermates/main/docker-compose.yml -o docker-compose.yml
curl -fsSL https://raw.githubusercontent.com/customermates/customermates/main/.env.selfhost.template -o .env
```

Then edit `.env` with real values:

- `BETTER_AUTH_SECRET`: a long random string (`openssl rand -hex 32`).
- `POSTGRES_PASSWORD`: change the default.
- `BASE_URL`: your public URL (e.g. `https://crm.example.com`). Defaults to `http://localhost:4000` for local.
- `RESEND_API_KEY` and `RESEND_OPERATOR_EMAIL`: a configured [Resend](https://resend.com) project. Required for signup verification, password reset, and invitation emails. `EMAIL_TRANSPORT` picks how mail leaves: `resend` (the default in production), `smtp` with the `EMAIL_SMTP_*` settings, or `console`, which writes each email to the server log instead of sending it and is the default outside production. An explicitly set transport sends in every environment, so a staging server with `EMAIL_TRANSPORT=resend` sends real mail.
- `RESEND_WEBHOOK_SECRET` (optional): the signing secret (`whsec_…`) of a Resend webhook pointed at `/api/webhooks/resend` for the events delivered, delivery delayed, bounced and complained. With it, each sent email's status moves to delivered, bounced or complained, and a hard bounce or a complaint adds the address to the suppressed addresses so marketing mail is not sent to it again. Without it the route answers 404. The SMTP transport reports acceptance only, so it has no delivery tracking.
- `AUTOMATION_SCHEDULE_ENABLED` (optional, default `false`): automations with the **On a schedule** trigger fire only when this is `true`. The five-minute automations job always runs, so runs whose workflow ended without settling them are still marked failed (never restarted), and a schedule that is more than an hour overdue, for example after a long stop, moves to its next time instead of firing the missed ones. Before turning it on, review which scheduled automations are enabled.
- `WEBHOOK_ALLOW_PRIVATE_HOSTS` (optional, default `false`): webhooks and the automation action **Call a URL** refuse URLs that point to private, loopback or link-local addresses (for example `127.0.0.1`, `10.x`, `169.254.169.254`), checked when saving and again before each request. Set it to `true` only when they must reach services inside your own network.
- `CLAMAV_HOST` and `CLAMAV_PORT` (optional, port default `3310`): a ClamAV daemon (`clamd`, for example the `clamav/clamav` image) that scans every uploaded record file before it is kept and every email attachment before it is stored. An infected upload is deleted and refused; while the configured daemon is unreachable, uploads are refused rather than kept unscanned, and attachments are left unstored. Without `CLAMAV_HOST` nothing is scanned.
- `MAILBOX_GOOGLE_CLIENT_ID` and `MAILBOX_GOOGLE_CLIENT_SECRET`, `MAILBOX_MICROSOFT_CLIENT_ID` and `MAILBOX_MICROSOFT_CLIENT_SECRET` (optional): OAuth clients that let users connect Gmail or Microsoft 365 mailboxes by signing in instead of with an app password. Register `<BASE_URL>/api/mailbox/oauth/google/callback` or `<BASE_URL>/api/mailbox/oauth/microsoft/callback` as the redirect URI. Google needs the `https://mail.google.com/` scope (and `calendar.readonly` for calendar sync), which Google treats as restricted: a public app must pass Google's verification, so an internal (Workspace-only) app is the quick path. Microsoft needs the delegated `IMAP.AccessAsUser.All`, `SMTP.Send`, `offline_access` and, for calendar sync, Microsoft Graph `Calendars.Read` permissions, and the tenant must allow IMAP and authenticated SMTP for the mailbox. `MAILBOX_MICROSOFT_TENANT` (default `common`) limits sign-in to one tenant. `MAILBOX_SECRET_KEY` must be set, since the tokens are stored sealed with it. A provider without both values is not offered.
- `STORAGE_QUOTA_MB` (optional): the most each workspace may store, in megabytes, counting record files, documents and stored email attachments. An upload that would exceed it is refused, and new email attachments are no longer stored; signed documents from the e-signature provider are always kept. `GET /v1/storage/usage` reports the bytes used and the quota. Without it storage is unlimited.
</Step>

## Day-to-day operations

### Update

```bash
docker compose pull
docker compose up -d
```

Pulls the latest app image and restarts the affected services. Migrations run automatically on container boot. Verify with `docker compose ps`.

### Apply configuration changes

```bash
docker compose up -d
```

Reconciles the stack and recreates affected containers when configuration changed. Use it after `.env` changes. For a simple restart with unchanged configuration, `docker compose restart` is sufficient.

### Logs and troubleshooting

```bash
docker compose logs -f app
docker compose logs -f postgres
docker compose ps
docker compose exec app sh
```

Enabled background jobs run in-process through the Postgres-backed worker that starts with the application. There is no separate worker service in the Compose file. Inspect application logs with `docker compose logs -f app`.

### Reset all data

```bash
docker compose down -v
docker compose up -d
```

`-v` deletes the Postgres volume. IRREVERSIBLE. Take a backup first if you need the data.

## File storage

Files, such as record attachments and the documents and invoices the app generates, live in an S3-compatible bucket, not in Postgres. Any S3-compatible service works: a managed bucket (AWS S3, Hetzner, Cloudflare R2, Backblaze B2) or a self-hosted server such as SeaweedFS or Garage. MinIO no longer publishes free community images. Without `STORAGE_*` variables the app still starts and file features stay unavailable. Set the four required variables together; a partial configuration stops the app at boot with a message naming what is missing.

| Variable | Required | Meaning |
|---|---|---|
| `STORAGE_ENDPOINT` | yes | Origin the app uses for its own requests to the bucket |
| `STORAGE_BUCKET` | yes | Bucket name |
| `STORAGE_ACCESS_KEY_ID`, `STORAGE_SECRET_ACCESS_KEY` | yes | Credentials with read, write and delete on the bucket |
| `STORAGE_PUBLIC_ENDPOINT` | no | Origin browsers reach, when it differs from `STORAGE_ENDPOINT` (a reverse proxy, a public hostname) |
| `STORAGE_REGION` | no | Defaults to `us-east-1` |
| `STORAGE_MAX_UPLOAD_MB` | no | Largest single upload, default 25 |

Browsers upload and download directly against the bucket through links signed for 15 minutes. A link is signed for one host, so `STORAGE_PUBLIC_ENDPOINT` must be exactly the origin browsers use, and the server clock must stay within 15 minutes of true time. The bucket must also accept your site as a cross-origin caller. From a checkout of this repository, with the same `STORAGE_*` values and `STORAGE_ENDPOINT` set to an address reachable from where you run it:

```bash
yarn storage:setup
```

It creates the bucket if needed, allows `PUT`, `GET` and `HEAD` from `BASE_URL` (or from each `--origin` you pass), and finishes with the preflight a browser sends. You can instead set the same CORS rule in your provider's console.

## E-signature (DocuSign)

Documents can be sent for signature through DocuSign when an integration is configured. Without `DOCUSIGN_*` variables the app starts normally and documents stay manual: you upload the executed PDF yourself. Set the four required variables together; a partial configuration stops the app at boot with a message naming what is missing. Signing also needs file storage.

| Variable | Required | Meaning |
|---|---|---|
| `DOCUSIGN_INTEGRATION_KEY` | yes | The integration key (client ID) of your DocuSign app |
| `DOCUSIGN_USER_ID` | yes | The API user's GUID; envelopes are sent in this user's name |
| `DOCUSIGN_PRIVATE_KEY` | yes | The app's RSA private key in PEM form; `\n` escapes are accepted for a single-line value |
| `DOCUSIGN_CONNECT_HMAC_SECRET` | yes | A Connect HMAC key from DocuSign's admin settings, used to verify callbacks |
| `DOCUSIGN_AUTH_SERVER` | no | `https://account.docusign.com` by default; `https://account-d.docusign.com` for the developer sandbox |
| `DOCUSIGN_ACCOUNT_ID` | no | The account to send from, when the user has more than one; the user's default account otherwise |

1. In DocuSign, create an app with **JWT grant**, generate an RSA key pair for it, and note the integration key and the API user's GUID.
2. Grant consent once, signed in as the API user: open `{auth server}/oauth/auth?response_type=code&scope=signature%20impersonation&client_id={integration key}&redirect_uri={a redirect URI registered on the app}` and accept. Until then sending fails with a message that consent is missing.
3. In **Settings → Connect → HMAC**, create a key and put it in `DOCUSIGN_CONNECT_HMAC_SECRET`. The app asks for HMAC-signed callbacks on every envelope and rejects any callback without a valid signature.
4. Make `{BASE_URL}/api/webhooks/docusign` reachable from DocuSign. Each envelope carries this callback address, so no Connect configuration is needed beyond the HMAC key. When callbacks cannot reach the installation, **Refresh signature status** on a document asks DocuSign directly.

## Backups

Back up Postgres with `pg_dump` on a schedule, and the storage bucket with your provider's tools when files are configured. The app container is stateless.

```bash
mkdir -p backups
docker compose exec -T postgres sh -c 'pg_dump -U "$POSTGRES_USER" "$POSTGRES_DB"' \
  | gzip > backups/customermates-$(date +%Y%m%d).sql.gz
```

For production:

- Schedule daily dumps to a separate volume or off-site storage.
- Test restore procedures in a non-production environment.
- Keep `.env` and secrets out of source control.

## Edition boundary

Every self-hosted deployment uses Starter entitlements. Connected messaging accounts, the unified inbox, connected calendar view, hosted Mate and hosted AI credits are cloud-only capabilities and are not unlocked in self-hosting by a paid cloud plan. External AI clients remain available through MCP. Review `LICENSE` and `ee/LICENSE.md` in the repository for the exact code-license boundary.

The hosted in-app Assistant is cloud-only and remains release-gated. External MCP uses your own AI provider. Enterprise SSO and white-labeling are not implemented in either deployment model.
