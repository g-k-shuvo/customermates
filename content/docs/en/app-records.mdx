Customermates has five record types: Contacts, Organizations, Deals, Services, and Tasks. They all use the same screen layout, so this page documents them together for people and for AI agents that drive the UI.

## What is the shared layout of a record type?

Every record type has the same three surfaces:

- **List** at `/{type}` (for example `/contacts`), locale-prefixed like `https://customermates.com/en/contacts`. Search, filter, sort, saved views, and bulk actions live here.
- **Add drawer**: the **Add** button opens a form over the list; the deep link is `?open={entityType}:new` (for example `/contacts?open=contact:new`). The drawer is for adding only; existing records open on their detail page.
- **Detail page** at `/{type}/{id}` (for example `/contacts/42`) for the full record, custom fields, relations, and delete. It opens with an overview of the fields that matter most; every field carries a pin control (no stable id) that adds it to or removes it from that overview. Pinning is per person, so two colleagues can read the same record through different summaries.

Rows never carry a DOM id. Open a record by its detail URL, never by clicking a row you located by id.

## Which ids does each list have?

Each record type has its own route and its own toolbar ids, prefixed with the type. The toolbar controls behave the same everywhere: **Add** opens the create drawer, **Search** live-filters the list, **Filter** opens the filter palette ([filter syntax](/docs/filter-syntax)), **Display options** controls columns, sorting, and layout, and the transfer menu exports the list to a spreadsheet or imports records from one.

| Contacts | `/contacts` | `contact` | `#nav-contacts` | `#contacts-add`, `#contacts-search`, `#contacts-filter`, `#contacts-display-options`, `#contacts-transfer` |
| Organizations | `/organizations` | `organization` | `#nav-organizations` | `#organizations-add`, `#organizations-search`, `#organizations-filter`, `#organizations-display-options`, `#organizations-transfer` |
| Deals | `/deals` | `deal` | `#nav-deals` | `#deals-add`, `#deals-search`, `#deals-filter`, `#deals-display-options`, `#deals-transfer` |

Inside each display-options popover, the layout controls are `#{type}-layout-table` and `#{type}-layout-board`, for example `#contacts-layout-table`, `#contacts-layout-board`, `#organizations-layout-table`, `#organizations-layout-board`, `#deals-layout-table`, `#deals-layout-board`, `#services-layout-table`, `#services-layout-board`, `#tasks-layout-table`, `#tasks-layout-board`. Every id in this section is a target the hosted assistant can navigate to or highlight.

## How do I import or export records?

The transfer menu (`#{type}-transfer`, for example `#contacts-transfer`) on every list is labelled **Import and export**. **Export** writes the current list to an Excel workbook with the visible columns, the current filters, search and sort applied, or only the selected rows when some are checked; the first 50,000 records are included. **Add from file** opens a wizard that reads an Excel workbook (`.xlsx`, up to 10 MB and 10,000 rows), lets you match spreadsheet columns to fields, custom fields and channels, checks every row, and then adds the records in batches. A column mapped to **Record ID** updates existing records instead of adding new ones. CSV files are not accepted: save them as `.xlsx` first. Over MCP, the equivalent of an import is one `create_contacts`, `create_organizations`, `create_deals`, `create_services`, or `create_tasks` call with up to 100 records.

## How do saved views work?

The saved-view tabs sit directly under the header on every list surface, and they carry the same ids everywhere, so these ids have no record-type prefix. A view belongs to the user who created it and remembers the whole list: filters, search, sort, page size, layout, grouping, column order, column widths and hidden columns. Every change is saved into the active view as you make it; on the All tab it is saved as your personal state for that list. There is nothing to reset or save by hand. A new view is private. Its owner can choose **Share with team** in the menu so that everyone in the workspace sees it on the same list, marked with a team icon, after their own views; **Stop sharing** makes it private again. Only the owner can edit, move, share or delete a view. A teammate who opens a shared view can change its filters on screen, but those changes are not saved to it (a notice says so); **Duplicate as new view** keeps them in a private copy of their own. When a shared view disappears, anyone who had it open lands on All.

- `#global-data-views` is the tab bar itself, a navigation landmark.
- `#global-data-views-all` is the built-in All tab, which clears the active view.
- `#global-data-views-new` opens the create-view overlay.
- `#global-data-views-menu` opens the action menu for the active tab: edit, duplicate, move, share or stop sharing, copy link and delete on a view of your own; duplicate plus copy link on a view a teammate shared, under a note naming who shared it; and duplicate plus copy link on the All tab.
- `#global-data-views-ai` is **Ask AI** inside the right-hand view-actions menu. Clicking a view selects it and opens this same menu. Ask AI opens chat with the exact view attached as a removable context chip and editable starter text; it does not send a message.
- **Ask AI** is also available while editing a view and at the top right of the Filters and Appearance headers, including nested filter pages. Pending filter changes are applied before chat opens. Asking from the edit dialog does not save an unfinished rename. The selected view id, surface, and requested create or update action stay attached independently of the translated starter text.
- `#view-editor-ai` offers **Create with AI** inside **New view** and carries its optional name in the canonical create context, chip label, and starter text. Opening chat creates no view and sends no message.
- On list pages, the chat composer’s **Add** menu can attach the current view or the **New view** action again later. On record detail pages it offers the current record instead; its search can attach another contact, organization, deal, service, or task. The activity timeline Ask AI action attaches both the record and its timeline target directly, so a linked deal cannot change a Contacts or activity-view target.

A view is addressed by the `view` query parameter, for example `/deals?view=<id>`; without it, the page uses your remembered selection. Use `view=__all__` to open All explicitly. The tabs themselves carry no ids, so switch views by URL rather than by clicking a tab you located by id.

Describe the records you want to see, for example “Create a view of my open deals, sorted by value.” The assistant uses `manage_data_views` to discover the page’s supported settings, then saves filters, search, sorting, grouping, page size and layout. It preserves settings you did not ask to change. New views are selected automatically; changes appear after the chat turn finishes. The assistant cannot share a view or change a teammate's shared one, and deleting a view requires confirmation in the built-in chat. Column visibility, widths and order stay available in Appearance. External AI clients connected through MCP can use the same tool with the connected user’s permissions.

## What is special about each record type?

**Contacts** are people, with channel identifiers (email address, phone, LinkedIn, WhatsApp, Instagram, Telegram) that connect them to Inbox threads and power the send icons on their detail page. **Organizations** group contacts and carry the company-level relations that deals and services hang off. **Deals** track opportunities and carry linked services with per-deal quantities; the deal's total value and quantity follow from them, and a weighted value follows from the stage column when the workspace defines one (see [core concepts](/docs/concepts#how-does-a-weighted-pipeline-work)). A deal's form also holds its expected close date and its own probability, which overrides the stage's default. **Reopen** on a won or lost deal puts it back in the open stage it left when it was closed, or in the first stage when that is unknown. A deal converted from a lead links back to it (**From lead**), and the lead links to its deal. **Services** are what you sell, linkable to deals and organizations. **Tasks** are to-dos that link to any of the other types and to assignees. Tasks have no built-in due date: add a Date custom column called "Due date" and filter or sort on it.

All five share the same machinery: the same list views, the same drawer and detail page, the same custom columns, the same filters, and the same relation editing. Anything this page says about one type holds for the others.

## How do I switch between table and board view?

Every list offers a table and a board. `#{type}-display-options` opens the switcher, which shows one labelled card per layout with a small preview of it; the board groups records by a field, and the group-by picker lists every groupable field: `singleSelect` custom columns, linked records, assigned users, and created or updated dates. A board with no grouping yet asks you to pick one and offers to create a `singleSelect` field on the spot. Sorting, search, and filters live in the same toolbar (`#{type}-search`, `#{type}-filter`). View choices persist per user and survive reloads. When you ask for guidance, the hosted assistant can highlight search, filter, display options, and the table or board targets, and you open and change those controls yourself. **Ask AI** in the view, Filters, or Appearance can instead apply supported saved-view settings through chat.

The filter control opens a command palette. `#filter-palette-search` narrows the list of filterable fields as you type; picking a field opens its value page, and the value applies to the list as soon as you set it, with no separate apply step. `#filter-palette-back` returns to the field list, Escape steps back one page and closes the palette at the top level, and **Clear** removes every applied filter at once.

## How do I change a deal stage or a task status on the board?

Any record type can carry user-defined custom columns. There are no fixed workflow fields baked into a type, so there is no product-level deal stage or task status. A `singleSelect` custom column holds those values, and `get_record_schema` returns whatever columns a workspace has configured for each type with their option values.

To change a stage in the app, open the record and set the field, or drag the card between board columns when the board groups by that column. Over MCP, call `update_deals` or `update_tasks` with the column id and the option value from `get_record_schema`; the option value is the canonical form, not the label.

A `singleSelect` custom column can drive a board (kanban) view. `#{type}-display-options` switches the list between a table and a board, and the board groups by the chosen field. This applies to every record type, not only to deals.

The demo workspace ships example columns to illustrate the pattern, for instance a "Stage" column on deals and "Status" and "Priority" columns on tasks. These are seeded examples, not fixed behavior. Rename them, change their options, add more, or remove them per workspace.

Records link to other records through labeled relation fields inside the form. Pick the records, then save. Over MCP, `manage_record_links` adds or removes single links.

## How do files work?

Contacts, organizations, deals and leads have a **Files** tab on their detail page; when a lead is converted, its files move to the new deal. Choose **Upload files** or drop files onto the tab; each file goes straight from the browser to the workspace's file storage, then appears in the list with its size, who uploaded it and when. Clicking a name opens a PDF or an image in a new tab and downloads anything else. Removing a file deletes the stored copy too. An upload whose content does not match its file type, such as a program renamed to `.pdf`, is deleted and refused.

Only common business formats are accepted: PDF, images, text and CSV, Word, Excel, PowerPoint and OpenDocument files, ZIP archives, calendar and contact cards, email messages, and audio and video. The extension has to match the file's type. HTML, SVG, XML, scripts and executables are always refused. The size limit is shown on the tab (25 MB unless the installation changes it).

Anyone who can open the record sees its files; adding and removing them needs edit permission on that record type. The tab only offers uploads when the installation has file storage configured (see [self-hosting](/docs/self-hosting#file-storage)). An upload that never finishes is discarded after a day, and the files of a deleted record are removed with it. Over the API, the same flow is `POST /v1/files/uploads`, then a `PUT` of the bytes to the returned URL, then `POST /v1/files/{id}/complete`.

## How do documents work?

Contacts, organizations and deals also have a **Documents** tab for contracts and other papers that go out for signature. Choose **Add document** and pick one or more PDFs; each becomes a document titled after its file name, with the status **Draft**. Only PDF files are accepted, up to the same size limit as files.

Each document shows who added it and when, and a status you set from its row: **Draft**, **Sent**, **Signed**, **Declined** or **Voided**. When the executed copy comes back, choose **Attach signed copy** in the row's menu: the document keeps the PDF as you uploaded it, adds the signed copy and moves to **Signed**. Attaching another signed copy replaces the earlier one. Clicking a title opens the signed copy when there is one, otherwise the PDF as uploaded; the menu opens either one, renames the document or deletes it together with its PDFs.

Documents follow the same rules as files: anyone who can open the record sees them, and adding, changing or deleting them needs edit permission on that record type. Over the API, `POST /v1/documents` registers a document and returns an upload URL for its PDF, and `POST /v1/documents/{id}/files/{fileId}/complete` lists it once the bytes are stored. `POST /v1/documents/{id}/signed-copy` does the same for the executed copy, and `PUT /v1/documents/{id}` changes the title or the status.

When the installation has DocuSign configured (see [self-hosting](/docs/self-hosting#e-signature-docusign)), a draft, declined or voided document offers **Send for signature** in its menu. Choose the signers (the record's people with an email address are suggested), adjust the email subject and message, and send: DocuSign emails each signer, and the document shows **Sent** with how many have signed. While the request is out, its status cannot be changed by hand; **Cancel signature request** voids it instead. Once everyone has signed, the executed PDF from DocuSign becomes the document's signed copy, the status moves to **Signed**, and whoever added the document gets an email. A declined or voided request sets that status, and the document can be sent again. Over the API this is `POST /v1/documents/{id}/signature`, with `/signature/void` and `/signature/refresh` beside it.

## How do I find duplicate contacts and organizations?

On the contacts list, **Import and export** → **Find duplicates** opens **Duplicate contacts**. Choose **Scan for duplicates**: the scan runs in the background over every contact and lists groups of contacts that look like the same person, strongest first. Each group names the signals that matched: the same name (in any order and with accents folded, so Jürgen Müller matches Juergen Mueller), a similar-sounding name, the same email name, the same surname at the same company email domain, the same phone (its last seven digits, whatever the formatting) or the same surname at the same organization. A similar name alone is not enough to form a group. Values shared by very many contacts, such as a common office phone, are skipped and counted under the scan.

Choose **Merge** on a group to combine it into one contact. Pick the contact to keep (it keeps its id), and where names or custom fields differ, pick whose value to keep. The kept contact gains every channel, organization, deal, task, owner, lead, file, document and linked-record reference of the others, and their notes are appended to its own; the others are then deleted. **Recent merges** lists the last merges, and **Undo** (also offered in the confirmation toast) restores the deleted contacts under their own ids with everything they held, and returns the kept contact's names, notes and custom fields to what they were, for 30 days. Merging needs read access to all contacts and permission to update and delete contacts. Over the API this is `POST /v1/contacts/merge`, `GET /v1/contacts/merges` and `POST /v1/contacts/merges/{id}/undo`.

Choose **Not duplicates** on a group when its contacts are different people. That pair is then never grouped again by a later scan, not even inside a larger group. Each new scan replaces the groups the previous one left open. Finding and reviewing duplicates needs read access to all contacts, and dismissing a group also needs edit permission. Over the API this is `POST /v1/duplicates/scans`, `GET /v1/duplicates/groups?entityType=contact` and `POST /v1/duplicates/groups/{id}/dismiss`.

Organizations have the same page: **Import and export** → **Find duplicates** on the organizations list. It matches organizations by name with legal forms such as GmbH, AG, Inc. or Ltd. left out (so Acme GmbH matches ACME), by a similar-sounding name, and by a company email domain their contacts share. Merging organizations moves their contacts, deals, owners, tasks, leads, files, documents and linked-record references to the one you keep, appends their notes, and can be undone for 30 days in the same way (`POST /v1/organizations/merge`, `GET /v1/organizations/merges`, `POST /v1/organizations/merges/{id}/undo`).

Groups also open outside a scan. A web form submission from a new email address creates a new contact, and when that contact looks like an existing one (same name, same company email domain with the same surname, same phone) a group opens for review; the two are never merged automatically. An import of contacts or organizations with **Match existing records by** set and **When a match is found** set to **Add and queue for duplicate review** adds each matching row as a new record and opens a group with the records it matched, even when it matched several.

## How do invoices work?

**Invoices** in the sidebar lists every invoice, newest first, with its number, recipient, status, dates, total and what is still open; the buttons above filter by status. An invoice starts as a **Draft**: choose **New invoice** there, or open a deal's **Invoices** tab and choose **New invoice** to start from the deal. A draft from a deal gets one line for the deal's base value and one per service on it, at the default tax rate, and is billed to the deal's first organization. On a draft you edit the recipient, currency, due date, notes and lines (description, quantity, unit price, discount and tax rate); totals, tax per rate and the open balance are worked out to the cent as you type. A draft has no number and can be deleted.

**Issue** gives the draft the next number from the invoicing settings (prefix plus a four-digit sequence, such as RE-0001), today's date, a due date from the payment terms unless you set one, and a copy of your company's details as the seller. From then on it cannot be edited or deleted; later changes to the settings do not alter it. Issuing needs your company's legal name and address in the invoicing settings, the recipient's name and address on the invoice, and at least one line. On an issued invoice, **Record payment** adds a payment with its amount, date and an optional note; when the payments cover the total the invoice becomes **Paid**, and a payment larger than the open balance is refused. **Undo** on the confirmation removes a payment entered by mistake; a paid invoice whose payments no longer cover the total goes back to issued. **Void** cancels an issued, unpaid invoice; it keeps its number, so the sequence has no gaps. An issued invoice past its due date shows **Overdue**.

**Download** on an invoice saves it as an A4 PDF in your display language: a draft is marked as a draft and a voided invoice as void, and an issued one shows the seller details it was issued with. An issued or paid invoice can also be downloaded as **XRechnung**, the German e-invoice (XRechnung 3.0 in UBL, which also meets EN 16931). It needs your company's billing email, phone, VAT ID and an address with postcode and city in the invoicing settings, and the recipient's billing email and address; until then the menu lists what is missing. VAT is reported as standard rated for a positive rate and zero rated for 0 %; an IBAN in the bank details becomes a SEPA transfer instruction. Over the API this is `GET /v1/invoices/{id}/pdf` and `GET /v1/invoices/{id}/xrechnung`, both with an optional `locale`.

An organization's **Invoices** tab holds its billing details (legal name, address, VAT ID and billing email), which new invoices for it start from, beside its invoices. Invoices have their own permission in each role: **Read access** is none or all, and **Manage** covers creating, editing, issuing, recording payments and voiding. Over the API this is `GET` and `POST /v1/invoices`, `GET`, `PUT` and `DELETE /v1/invoices/{id}`, `POST /v1/invoices/{id}/issue`, `/payments` and `/void`, `DELETE /v1/invoices/{id}/payments/{paymentId}`, and `GET` and `PUT /v1/organizations/{id}/billing-profile`.

## How do automation triggers and conditions work?

An automation on **Automations** starts when a record of its type is created, updated or deleted, or on a schedule. For an update, **Only when these fields change** limits it to updates that touched one of the chosen fields, and **Only when the record matches** limits it to records that meet the conditions, written in the same filter language as the lists, including a deal's stage and pipeline and custom fields. Together they express a stage transition: with the stage as the changed field and the stage condition set to one stage, the automation runs exactly when a deal moves into that stage, and not on any other edit of the deal. A run whose record does not match is recorded as skipped. Over the API this is `GET` and `POST /v1/automations`, `PUT` and `DELETE /v1/automations/{id}` and `GET /v1/automations/{id}/runs`; conditions use the filter objects of the list endpoints, for example `{ "field": "stageId", "operator": "in", "value": ["<stage id>"] }`.

A change an automation makes can start other automations, up to three in a row: if automation A moves a deal into a stage, automation B on that stage transition runs too, and so can a C that B sets off, but nothing after that. An automation never runs again inside a chain it already started, so A setting off B setting off A stops at B, and one run starts each follower at most once per record. Every run on a contact, organization, deal, service or task is shown in that record's activity as **Automation ran**, under the name of the automation's owner, with the automation's name in the detail view.

## Who does an automation email go to?

The **Send an email** action sends to a fixed address, to the triggering record's contact (a contact itself, a deal's first contact, or a lead's contact, using the contact's first email address) or to the record's owner (a lead's owner, or the first active user assigned to a deal, contact, organization or task). The subject and text use the same Markdown and merge fields as email templates, such as `{{ contact.firstName }}` or `{{ deal.name }}`, filled from the triggering record. When the record has nobody to send to, or a merge field has no value and no default, the step fails with that reason and nothing is sent. The email is written in the owner's language when it goes to the owner, and otherwise in the language of the user the automation runs as. Over the API the recipient is `{ "kind": "address", "address": "…" }`, `{ "kind": "recordContact" }` or `{ "kind": "recordOwner" }`; an older step that still stores `to` keeps working as a fixed address.

## How do I set up automation actions?

Each action in the automation dialog shows its own fields: people are picked from the workspace's active users, a deal's stage is picked from a pipeline and then one of its stages, a wait is a number of minutes, hours or days, and an email's text has buttons that insert merge fields. **Set a field** offers the record's writable fields, including custom fields of the types text, email, phone, link, currency, single select, date and date with time; the value is checked against the field's type when the step runs, so a currency field takes a number and a single-select field one of its options. A deal's stage is changed with **Move to a stage**, never with **Set a field**, so the stage history stays complete. To hand a won deal to delivery, create an automation on deals with **Only when these fields change** set to the status, a condition that the status is won, and a **Create a deal** action in the Delivery pipeline at its first stage.

## How do contact lists work?

**Lists** in the sidebar groups contacts for campaigns. A contact can be on any number of lists, and each list name is unique in the workspace. **Add contacts from a filter** adds every contact that matches a search and the same filters as the contacts list, in the background and in pages, so even thousands of contacts are added without a selection limit; contacts already on the list stay once, and only contacts you may see are added. The progress shows while it runs, and when it finishes the count is checked again, so a change made meanwhile is visible. Removing a contact from a list, or deleting a list, never deletes the contact. Over the API: `GET` and `POST /v1/contact-lists`, `GET`, `PUT` and `DELETE /v1/contact-lists/{id}`, `GET` and `POST /v1/contact-lists/{id}/members` (up to 100 contact IDs), `POST /v1/contact-lists/{id}/members/remove`, and `POST /v1/contact-lists/{id}/fill`, which returns a job to follow with `GET /v1/bulk-jobs/{id}`.

## How do campaigns work?

**Campaigns** in the sidebar (for roles with the campaigns permission) sends one email to an audience of contacts. A draft has a subject and a Markdown message with the same merge fields as email templates, filled per contact, an optional sender, and an **audience**: conditions that must all match: on a list, not on a list, a contact field, or a field of the contact's organization, for example on the list *CDI Targets* and the organization's industry is *Higher Education*. Conditions can also be grouped: in an **any of** group one condition is enough (for example industry is *Higher Education* or the role is *Dean*), and a **none of** group excludes contacts matching any of its conditions (for example not on *Opted out* and not at a *Retail* organization). Groups contain conditions, not further groups. **Preview audience** shows how many contacts qualify, how many match but have no email address, and the first 25. A campaign cannot be sent until its **lawful basis** is recorded; recording it documents why the recipients may be emailed but does not make the send lawful. For advertising email to recipients in Germany that usually means their prior consent, which only whoever is responsible for data protection can confirm. When you send, the audience is resolved once in the background, then mail goes out in small batches: each contact receives it at most once even if sending is interrupted, suppressed and unsubscribed addresses are skipped, and every message carries a one-click unsubscribe link. Opens and clicks are not tracked. **Stop sending** ends a running campaign; everyone not reached yet is skipped. 180 days after a campaign finishes, its recipient addresses are removed; the counts and the suppression list are kept. Over the API: `/v1/campaigns`, `/v1/campaigns/{id}`, `/v1/campaigns/{id}/recipients`, `/v1/campaigns/{id}/send`, `/v1/campaigns/{id}/cancel` and `POST /v1/audiences/preview`.

## How are new leads assigned an owner?

**Lead assignment** (Company settings, then Manage rules) gives a new lead that has no owner one automatically. Rules are tried in their order; the first enabled rule whose conditions the lead matches assigns it, either to **one person** or **in turn** to its people, skipping anyone who is no longer active. Conditions use the same filters as the leads list, so a territory is simply a rule whose conditions name the region, for example a country field; a rule without conditions catches every lead. To route web-form leads by region, add a single-select lead custom field such as *Region*, map the form's region field onto it under **More fields** on the web form source, and add one rule per region whose condition is that value. This applies to leads created by hand, over the API, in bulk and from web forms, and it happens before the new-lead notice and follow-up task go out, so they reach the assigned owner. A lead created with an owner keeps it. Over the API: `GET` and `POST /v1/lead-assignment-rules`, `PUT` and `DELETE /v1/lead-assignment-rules/{id}`.

## How do email templates work?

**Automations** → **Email templates** (`/automations/templates`) keeps reusable emails: a name, a type, a subject and a body written in Markdown. The body is stored as Markdown and turned into email-safe HTML only when a message is sent; raw HTML in a template is shown as text, never run. **Transactional** templates are for one-to-one follow-ups; **Marketing** templates carry an unsubscribe link and are held back for anyone who unsubscribed, bounced or complained.

Email text in templates, campaigns and the **Send an email** action can use headings, bold and italic, lists, quotes, links, horizontal rules and images: `![description](https://…)` places an image at the width of the email. Only `https` images are kept; an image from any other address is dropped, and tables and raw HTML are not supported. A campaign, a template and a **Send an email** action can also carry a **Header image**, an `https` link to a picture shown across the top of the message above the text (600 px wide works best). Images are loaded from their own address when the recipient opens the email, so host them somewhere that stays online.

Merge fields fill in the record a message is about: `{{ contact.firstName }}`, `{{ contact.lastName }}`, `{{ contact.fullName }}`, `{{ contact.email }}`, `{{ organization.name }}`, `{{ deal.name }}`, and the sender's `{{ sender.firstName }}`, `{{ sender.lastName }}`, `{{ sender.fullName }}` and `{{ sender.email }}`. For a deal or lead, the contact is its first one. Give a field that a record may lack a default, as in `{{ contact.firstName | "there" }}`; without one, a message to such a record is not sent rather than going out with a gap. A field outside this list, or one written wrongly, is refused when the template is saved. Merged values are inserted as plain text, so a name can never add a link or formatting.

The preview beside the editor renders the template the way it would be sent, against a deal, contact or organization you pick, with you as the sender. Templates need permission to read automations; creating, changing and deleting them needs permission to edit automations. Over the API this is `GET` and `POST /v1/message-templates`, `GET`, `PUT` and `DELETE /v1/message-templates/{id}`, and `POST /v1/message-templates/preview`.

Every marketing email carries an unsubscribe link and the `List-Unsubscribe` and `List-Unsubscribe-Post` headers, so mail clients show their own unsubscribe button (RFC 8058 one-click). The link opens a page that asks to confirm; the mail client's button unsubscribes in one step, without a login. The address is then suppressed with the reason **Unsubscribed**, and marketing mail to it is held back from then on; transactional mail still reaches it. Unsubscribe links are stored only as a hash. **Company → Settings → Suppressed addresses** lists every suppressed address with its reason, and lets you add one by hand or lift a suppression. Over the API this is `GET` and `POST /v1/suppressions` and `DELETE /v1/suppressions/{id}`.

**Company → Settings → Sender** sets the name and address automations and campaigns send from, and an optional Reply-To. A custom address needs its domain verified: add the TXT record shown (`_crm-verify.<domain>`) at your DNS provider and choose **Check domain**. Until it is verified, and again after the address moves to another domain, those emails are refused rather than sent from another address, because a silent fallback is how mail lands in spam. With **Send as the user who triggered a message**, mail sent on a user's behalf goes out from that user's own address when it is on the verified domain. Without a sender set, mail goes out from the installation's default sender; **Use the default sender** removes a custom sender and returns to it. Over the API this is `GET`, `PUT` and `DELETE /v1/sender-identity` and `POST /v1/sender-identity/verify`.

## Tips for agents

- The hosted assistant navigates by the target ids above (`navigate` with a target id, or with an entity and record id for a detail page) and highlights toolbar controls; it never opens the drawer for an existing record.
- External browser clients locate controls by the stable ids, for example `document.querySelector('#deals-add')`. Ids are identical across locales and viewports; visible labels are not.
- To open an existing record, build its page URL yourself: `/{type}/{id}`. Do not try to click a row.
- Prefer [MCP](/docs/mcp) tools over driving the UI when a tool exists. Creating or updating a record, or changing a `singleSelect` column value, is one tool call instead of a click sequence.
